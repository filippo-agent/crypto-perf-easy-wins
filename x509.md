# crypto/x509 performance audit

Baseline: `2ff5743d9fd52fac166225e75df0c2c1edf82abb`. Audit date: 2026-09-27.
Scope: all production Go/assembly under `src/crypto/x509`, including pkix and internal/macos. No production changes made by this audit. Timings remain for the coordinating parent. Added only `src/crypto/x509/perf_audit_test.go`; not compiled/run by this agent.

## Shortlist / recommended measurement order

1. **Canonical RSA-PSS parameters fast path:** tiny, high-confidence avoidance of two reflective ASN.1 decodes. Public certificate/CSR/CRL parsing. Best match for requested optimization style. Existing OpenSSL no-NULL fixture deliberately remains fallback.
2. **Extension duplicate detection with DER OIDs instead of decimal strings:** broadly applicable public ParseCertificate win; retains validation/error behavior and linear expected complexity.
3. **Do not construct final policy sets when their result cannot affect success:** three-line early return near the *end* of policiesValid. Full Verify measurement required; signature verification can dominate.
4. **Stream hostname validation labels instead of allocating a split slice:** public VerifyHostname, particularly many-SAN certificates. Straightforward iterator substitution, not a parser rewrite.

No numerical performance claims yet. Public benchmarks, not only helper microbenchmarks, are prepared.

## 1. RSA-PSS known encoding fast path

Source: `x509.go:409–414` existing DER parameter constants; `getSignatureAlgorithmFromAI`, `x509.go:439–501`, especially reflective decoding at 468–475. Every RSA-PSS certificate parse decodes the outer parameter sequence and a nested MGF1 hash AlgorithmIdentifier; the exact three encodings emitted by Go already exist in this file.

Minimal insertion **after** the non-PSS branch at line 463, preserving all fallback code:

```go
switch {
case bytes.Equal(ai.Parameters.FullBytes, pssParametersSHA256.FullBytes):
    return SHA256WithRSAPSS
case bytes.Equal(ai.Parameters.FullBytes, pssParametersSHA384.FullBytes):
    return SHA384WithRSAPSS
case bytes.Equal(ai.Parameters.FullBytes, pssParametersSHA512.FullBytes):
    return SHA512WithRSAPSS
}
```

Correctness: byte-for-byte match to existing known-valid DER implies every existing parameter check passes. No user-controlled state cached, no cryptographic operation changed. Retain fallback for optional NULLs, explicit default trailer, trailing data currently tolerated by ASN.1, and malformed encodings. Do not broadly require canonical parameter encodings; that would be a compatibility change.

Reach: ParseCertificate/ParseCertificates, ParseCertificateRequest, ParseRevocationList, and legacy CheckCRLSignature. This is a parse win, not an RSA-PSS signature-verification arithmetic win.

Expected impact: avoids all allocations/reflective parsing in this helper for exact matches. Potentially meaningful whole RSA-PSS certificate parse benefit, but no effect on ordinary PKCS#1/ECDSA certificates. Important workload caveat: inspected both existing PSS fixtures using a small DER reader: `rsaPSSSelfSignedPEM` contains the 54-byte Go-style SHA256 parameters and hits the fast path; `rsaPSSSelfSignedOpenSSL110PEM` contains the 50-byte encoding with absent NULLs and does **not**. Keep this control in benchmarks; do not claim coverage of all OpenSSL-produced PSS certificates.

Prepared: `TestAuditPSSFastPath` checks three canonical results against current parser, every one-bit mutation, all truncations, absent-NULL fallback, wrong signature OID. Model helper is test-only and falls back to production function. `BenchmarkAuditPSSAlgorithm` compares model/current helper; `BenchmarkAuditParseCertificate/{PSS,PSSOpenSSL,Google,Root}` measures actual production entry point before/after parent applies change. Existing `TestRSAPSAParameters` [sic], `TestRSAPSSSelfSigned`, CSR/CRL tests are relevant.

## 2. Avoid extension OID decimal formatting on successful ParseCertificate

Source: `parser.go:1134–1153`, especially `oidStr := ext.Id.String()` at 1148. `parseExtension` already validates and decodes the first field; the original DER slice is still available because cryptobyte.String was passed by value. Current duplicate detection renders every extension OID to decimal text only to use it as a map key. `encoding/asn1/asn1.go:233–245` builds that string with a 32-byte initial allocation and component-by-component numeric formatting.

Minimal replacement after successful `parseExtension(extension)`:

```go
var oidDER cryptobyte.String
// parseExtension already validated this OBJECT IDENTIFIER.
extension.ReadASN1(&oidDER, cryptobyte_asn1.OBJECT_IDENTIFIER)
oidKey := string(oidDER)
if seenExts[oidKey] {
    return nil, fmt.Errorf("x509: certificate contains duplicate extension with OID %q", ext.Id.String())
}
seenExts[oidKey] = true
```

This uses one cheap TLV extraction, not a second OID integer decode. ASN.1 validation stays in place, including minimal subidentifier encoding: reviewed `src/vendor/golang.org/x/crypto/cryptobyte/asn1.go:422–487` (`readBase128Int`, `ReadASN1ObjectIdentifier`). Thus accepted OIDs have unique DER content; comparing raw content is equivalent to comparing their decimal strings. The duplicate error retains the original decimal text. Existing `parseCertificatePoliciesExtension` already uses raw DER OID map keys (`parser.go:570–596`).

Expected impact: eliminates numeric formatting and shrinks map-key bytes for every extension. It does **not** eliminate the stored map-key string allocation. Broad certificate parsing applicability, including non-PSS. Extra TLV scan is tiny but benchmark it. Avoid replacing map with O(n²) slices/linear search: attacker-controlled extension counts make that unattractive.

Tests: existing `TestDuplicateExtensionsCert`, plus add duplicate same OID/different value and criticality; ensure non-minimal/overflow/truncated OIDs still fail with same parser error. Differentially parse normal and malformed certificate fixtures. Prepared public ParseCertificate benchmark includes standard Google certificate and GTS root. CSR duplicate detection would require more structural parsing changes because its path currently uses reflective asn1.Unmarshal; do not extend this patch there without separate justification.

## 3. Skip policy result construction when explicit policies are not required

Source: `verify.go:1358–1406`, `policiesValid`. After leaf RequireExplicitPolicyZero handling at 1364–1366, the only remaining rejection is `explicitPolicy == 0 && len(userConstrainedPolicySet) == 0` at 1402. The intermediate graph traversal, final set construction, and map clone have no externally observable effects when explicitPolicy is positive.

Insert immediately after line 1366:

```go
if explicitPolicy > 0 {
    return true
}
```

This preserves all main-loop policy mapping validation and all countdown/leaf constraints. **Do not** move the return before the loop or skip policy processing merely because VerifyOptions.CertificatePolicies is empty: invalid mappings can still reject a chain.

Expected impact: saves final graph traversal, slices, OID string copies, map construction and clone on common successful non-explicit-policy chains. No claim yet about total Verify speed. Prepared `BenchmarkAuditVerify` uses existing real Google/GTS chain, explicit trust pool/time, and warms lazy cert parsing before timing. `TestPoliciesValid`, `TestInvalidPolicyWithAnyKeyUsage`, `TestNISTPKITSPolicy` and limbo coverage should all pass unchanged.

Related separate micro-patch: at `verify.go:1206`, avoid allocating a graph which the first loop iteration immediately discards when `chain[n-1].Policies` is empty:

```go
var pg *policyGraph
if len(chain[n-1].Policies) != 0 {
    pg = newPolicyGraph()
}
```

Private PKI/no-policy chains may benefit more from this. Need a no-policy generated chain benchmark; the Google benchmark is not guaranteed to exercise this variant. Keep the changes independently measurable. The function is internal and called with nonempty chains; preserve that invariant rather than introducing a broader empty-chain behavior change.

## 4. Avoid splitting each SAN solely to validate it

Source: `verify.go:820–867` (`validHostname`), called once for requested host and once per candidate in `Certificate.VerifyHostname`, lines 958–980. `strings.Split(host, ".")` at 833 allocates a slice immediately discarded after sequential iteration.

Change to `strings.SplitSeq` with an explicitly tracked first-label flag (wildcards are only accepted at first label). Rest of ASCII/label validation stays unchanged. Example loop preamble:

```go
first := true
for part := range strings.SplitSeq(host, ".") {
    isFirst := first
    first = false
    // Existing body, replacing i == 0 with isFirst.
```

Expected impact: one fewer temporary slice per validation; meaningful VerifyHostname allocation reduction on many-SAN certificates, especially late matches. Not necessarily a significant complete TLS verification improvement for small certificates. Prepared `BenchmarkAuditVerifyHostname/{1,10,100}` uses successful final wildcard match and fixed three-label names. Existing TestValidHostname, TestMatchHostnames, TestVerifyBareWildcard, VerifyHostnameIPAddresses exercise edge cases; add/retain invalid UTF-8, empty labels, underscore/hyphen, wildcard placement and trailing dot cases.

`matchHostnames` at 876–902 separately allocates another split slice. Streaming that loop with an explicit final label-count equality check is possible, but adds more behavioral review than the pure validation substitution. Treat as follow-up; do not accidentally accept unequal label counts. `splitHostname(candidateName)` also lowercases a string already lowercased by VerifyHostname, but that scan-only duplication is small and its other caller needs normalization.

## Small or less compelling leads (not promoted without public measurement)

- `cert_pool.go:165–173`, findPotentialParents: allocates a fresh merged result even when all candidates are in matchingKeyID (usual single-parent case). `if len(oneKeyID) == 0 && len(mismatchKeyID) == 0 { return matchingKeyID }` before the final merge is a safe three-line fast path preserving order and nil behavior. No exposed aliasing: buckets are fresh local slices. Saves one slice allocation per matching chain edge, but public Verify signatures dominate. Could instead append buckets to the first; that may create growth churn for mixed buckets, so measure carefully.
- `oid.go:100–114`, appendBase128BigInt: uses a newly allocated shifted big.Int for every output byte, even for ordinary small components. A three-line `if n.IsUint64() { return appendBase128Int(dst, n.Uint64()) }` uses the existing encoding helper and preserves large-component fallback. Benefits public ParseOID/UnmarshalText; not certificate DER parsing, so narrower relevance. `BenchmarkAuditParseOID` includes common OIDs and >64-bit components. Test zero, 127/128, MaxUint64, 65-bit values, and first-component +80 overflow; existing OID tests have >64-bit vectors. Do not replace all big.Int text parsing with uint64 parsing (would reject supported OIDs).
- `x509.go:1880–1888`, CreateCertificate: parent==template self-signing marshals the same subject twice if RawSubject is absent. Reuse asn1Issuer for asn1Subject only on pointer equality; no need to compare/deep-cache Name. Safe but self-signed creation is less hot and signing dominates. Benchmark existing BenchmarkCreateCertificate with rich subject before proposing.
- `pkix/pkix.go:41–105`, RDNSequence.String: escape directly into the existing strings.Builder with WriteRune instead of allocating []rune and converting to string. Preserve original byte-index-based escaping and invalid UTF-8 replacement semantics. This is public formatting, not parse/verify throughput, so lower priority.
- `root_darwin.go:85–92` and `internal/macos/corefoundation.go:213–219`: hoist CFArrayGetCount outside loops. It currently crosses runtime/libc trampoline per iteration. Arrays do not mutate during either traversal. Clear local improvement, but tiny relative to SecTrustEvaluateWithError and unmeasurable on the Linux host; not a headline win.

## Rejected / already optimized / semantic hazards

- **CertPool.AppendCertsFromPEM parse twice** (`cert_pool.go:219–253`): deliberate memory strategy. Initial parse validates/indexes, then lazy parse only materializes used roots. Retaining initial full certificates changes long-lived memory use; do not call this accidental duplication.
- **Skip parsing already-hashed PEM certs:** AddCert accepts caller-constructed Certificate with arbitrary Raw, so haveSum membership alone does not establish that incoming DER successfully parses. Returning true without parsing can change AppendCertsFromPEM results. A separate loader-local known-valid cache is out of scope.
- **Cache constraint/name/public-key checks on Certificate:** exported fields and slices can be modified. Persistent cached validation could become stale; rechecking in each Verify preserves mutation behavior. Constraint code explicitly documents this for mailbox parsing. Sorting copies also protects exported slices from mutation.
- **Remove name validation inside each constraint layer:** repeated domainNameValid is visible in constraints.go:537–556, but relocating it must preserve validation order and which failing constraint/name reports first. No compelling small common-path win; ordinary unconstrained chains already return early at 589–590.
- **Remove IP.Mask allocation in newIPNetConstraints:** constraints with nonzero host bits require canonicalized copies, while originals must remain unchanged. Avoid a hand-written masking/sorting rewrite for marginal gains. ipNetworkSubset broadcast buffer is small and constraint-specific.
- **Flatten parseName directly to pkix.Name:** all four consumers immediately FillFromRDNSequence (certificate subject/issuer, CRL issuer, CSR subject), so temporary RDN grouping is unnecessary. Could save several allocations, but changes return type/four callers or adds awkward single-attribute temporary wrappers, and requires preserving multi-valued RDN order/non-string attributes. More review surface than the shortlist; keep as a follow-up if profiles show name parsing dominant.
- **Reuse parsed issuer as subject for self-issued certs:** would alias writable slices/attributes which are currently separately allocated. Requires cloning, reducing benefit and increasing semantic risk.
- **Skip signer self-verification or duplicate message hash** (`signTBS`): checking the signer is intentional. MessageSigner dispatch and algorithm/domain semantics prohibit casually substituting key.Sign or dropping verification. No hash cache/API refactor proposed.
- **RSA Precompute/Validate twice in PKCS#8/PKCS#1:** repeated Precompute on a valid precomputed key is a fast no-op; validation behavior and errors must stay. No large repeated primality/key-derivation operation found here.
- **EC parse/marshal validation:** SEC1 import normalizes tolerated legacy scalar padding then uses established ecdsa.ParseRawPrivateKey. Public/private ECDSA byte methods preserve key validation and use existing key state; do not bypass them to serialize big.Int fields manually. ECDH public keys are already retained by key type. Ed25519 PKCS#8 stores Seed without rederivation.
- **Re-encode TBS twice:** already avoided in CreateCertificate, CreateCertificateRequest, CreateCRL, CreateRevocationList via Raw fields. Public-key encoding is reused for SKID generation in CreateCertificate.
- **CSR marshal/unmarshal attributes** (`newRawAttributes`, 2132–2148; CreateCertificateRequest): real conversion overhead but deprecated arbitrary ASN.1 attributes complicate replacing the roundtrip. Empty-attributes fast return is safe but tiny relative to signing; not promoted.
- **Platform parse/copy results:** root_darwin/exportCertificate and Windows/extractSimpleChain reparse OS-selected certificate bytes intentionally, ensuring Go representation/validation and detached backing storage. Reusing arbitrary input objects or borrowing native bytes risks mutation mismatch/lifetime issues. Windows ECDSA signature recheck explicitly mitigates CVE-2020-0601; never remove it for speed.
- **System roots locking/caching:** existing sync.Once/lazy CertPool plus fallback synchronization preserves SetFallbackRoots behavior. No new persistent state recommended. Directory symlink deduplication already exists; skipping directories after reading a bundle changes trust contents.
- **Legacy PEM encryption:** digest buffer reused across MD5 KDF iterations; encryption has a documented copy/code-complexity tradeoff. Deprecated/insecure-by-design path is not an attractive optimization target; no changes to padding checks or secret-dependent work.
- **OID formatting API:** AppendText currently goes through String; a direct appender could avoid a temporary string but requires refactoring 70-line big-component handling. Small OID integer fast path above is less invasive. MarshalBinary/UnmarshalBinary copies are required for ownership.
- **Error-only formatting and table dispatch:** signature algorithm/EKU small linear scans and redundant error-side parsing do not justify complexity. Stringer output is generated and not a manual tuning target.
