# ECC low-cost accelerated P256 — preliminary lead (2026-09-27)

**Strongest localized lead:** duplicate the existing accelerated P256 Booth-window loops for public verification only; replace full constant-time table scans with direct public indexing and skip zero-digit additions. Keep the existing global generator tables, per-call arbitrary-point table, recoding, assembly formulas, scalar reduction, and final complete Add. No new assembly or reusable-public-key cache. No production files edited. Awaiting parent's public Verify profiles and timings; **not yet a demonstrated win**.

The user hypothesis is confirmed locally: `fips140/ed25519/ed25519.go:322` calls VarTimeDoubleScalarBaseMult; `fips140/ecdsa/ecdsa.go:492,497` calls the same ScalarBaseMult/ScalarMult methods used for secret scalars. Accelerated P256 (`nistec/p256_asm.go`) scans 43×32 affine table entries and 52×16 projective entries per verification. Generator windows have **zero intervening doublings already**, so a joint engine does not magically eliminate a second full doubling chain.

Prefer independent public helpers over a shared bool switch initially: bool selection adds a branch to every private window and enlarges the private audited routine. Duplication costs roughly 150–200 lines including wrappers/table setup, but leaves all signing/ECDH/keygen scalar loops byte-for-byte unchanged. A follow-up refactor should only be justified after public API gain and private neutrality are measured.

Direct primary-code comparison: local BearSSL revision `7bea48e5e850ab4cafbe68d3765cdaba13a86d6f`, `src/ec/ec_p256_m64.c:1260–1337` uses constant-time scanned 4-bit affine windows even for the multiplication called by verification; `:1681–1716` explicitly rejects a simplistic joint table because of exceptional points, table size, and complete-formula costs. This is inspiration/constraint, not a claim BearSSL implements the proposed public fast path.

Artifacts and detailed tests are being prepared outside production source. Generic/larger-engine alternatives are owned by the separate worker.

## Exact scope, safety, and review cost

- Baseline `f6653cda`; generated by `patches/make-ecc-lowcost.py`. Only two production-file diffs, neither applied. The accelerated file also builds on ppc64le/s390x; default amd64/arm64 are the performance targets. Purego and other curves use the original arithmetic fallback.
- Existing ScalarBaseMult, ScalarMult, private signing, ECDH and key generation routines remain **byte-for-byte unchanged**. No per-window public/secret bool was inserted into a secret routine. Added CombinedMultPublic is internal and documented public-only; its only added call site is verifyGeneric after point, r and s validation.
- Two new public-input loop bodies reuse `boothW5`/`boothW6`, all table layouts, scalar endian conversion/reduction, sign negation and point formulas. The arbitrary table is still constructed **on every operation**, with no cache. Both source scalars remain unmodified. Same 32-byte length rule and same modulo-n reduction, including 0/n/n+1/max inputs.
- New public loop skips additions for zero digits, branches around initial-infinity correction and indexes `table[sel-1]` only after sel!=0. Correct bounds are 1..16 and 1..32 (existing selector comments saying [0,15]/[0,31] appear off-by-one relative to actual Booth outputs; do not copy that assumption into a bounds proof). It does not change scalar recoding or remove any nonzero-digit doubling.
- `CombinedMultPublic` overwrites its receiver by design; it computes the generator component separately, then uses the existing complete Add. Equal/opposite/final-infinity are handled there. Infinity input is explicitly returned as just the generator component, before incomplete arbitrary-table formulas. No new formulas or field representation. Public direct lookup leaks scalar digits and point-dependent behavior, intentionally; never route nonce/private-key multiplication here.
- Incomplete assembly additions inside each single multiplication keep the original operation sequence whenever the digit is nonzero, and keep the original table-construction sequence. Skipping zero operations is algebraically neutral. The original private loop's undefined intermediate addition with an initial infinity was masked by MovCond; the public loop simply copies its first finite digit instead. Differential testing remains mandatory, especially n-1 and top-bit/Booth carry boundaries.
- Review cost: +165 lines in P256 (mostly duplicated existing code), +12 net verifier lines. This is much less than a new signed-window engine but not literally a one-line call-site fix. A common `public bool` could reduce source duplication substantially; its secret loop would still be constant-time with a fixed false parameter, but extra branches/inlining/layout changes require private Sign/ECDH benchmarks and broaden the audited routine. A shared table-preparation extraction could save ~45 duplicate lines, but introduces a helper call or inlining dependency into private code. Neither is justified before public results clear the bar.
- Old FIPS snapshots replace internal nistec and ECDSA coherently. Public-package code has no new internal method reference. No CAST/PCT/approved-service hook removal. Current-module FIPS review/ACVP tests still required; do not claim automatic validation equivalence. Public old-snapshot tests should remain compatible.
- No final-projective-X or binary inverse changes from round two are included. Existing final BytesX+mod-n handles rare valid x>=n exactly as before. No reusable-public-key premise.

## Mathematical counts vs profile vs measured result

The current arbitrary-point loop has 52 selected digits (top, 50 interior, bottom), 255 main-loop doublings, plus 8 precompute doublings and 7 precompute additions. Generator side has 43 selected digits and 42 affine additions, no scalar-loop doublings. Existing complete final Add computes an addition and doubling. Thus 43*32 + 52*16 = **2,208 table entries scanned** versus at most 95 direct selections. This is a large reduction in table traffic but only **3.00% sampled API time**, the important distinction.

Interior Booth-W5 zero probability is 2/64=1/32 and W6 zero probability 2/128=1/64 under uniform windows (boundary windows differ). Expected skipped ordinary additions are ~1.6 projective and ~0.65 affine. A rough profile-weighted saving is <1 percentage point; top-window initial-copy and eliminated MovCond calls may contribute further fractions of a percent. These are mathematical/profile estimates, **not measured API gains**. All ~263 arbitrary-point doublings remain, dominating the present profile. No arm64 profile or timing is available.

### Why sparse Q is still localized, and why it is not a huge gain

This is **not** a joint engine: G retains the existing 43 positional affine tables and no-doubling loop. Q retains the existing Jacobian representation, Montgomery arithmetic, negation and Add/Double assembly. The Q table consists of the same odd points Q,3Q,...,15Q already present in the private table, but constructs only those 8 points using **1 doubling +7 additions**, instead of building all 16 points with **8 doublings +7 additions**. No new global tables, no retained key state, no new assembly. The recoder is 32 lines with a 257-digit local buffer, including the top carry. Conceptually it is the same established width-5 signed recoding as the generic worker's prototype, specialized to existing P256 little-endian scalar limbs; if both proposals were ever selected, deduplicate recoding deliberately rather than blindly applying both dispatch patches.

The public Q loop seeds from its highest nonzero digit, does one existing doubling per remaining bit, and adds only at nonzero digits. It keeps addition **complete** with public branches: if the accumulator is infinity, copy the finite addend; otherwise existing p256PointAddAsm computes the sum and equality flag, and only equality triggers an extra doubling. Opposite-point results naturally have Z=0. Thus it does not call the existing complete Add, which would unconditionally compute a throwaway doubling at every digit; neither does it silently assume exceptional points cannot occur. The per-call table addends are finite because Q is checked finite and the curve has prime order >15. Existing complete final Add is retained unchanged.

Approximate counts (uniform normal 256-bit scalars, NOT timings):

- Original Q main loop: 255D+51A, including additions of zero-selected placeholders. Table: 8D+7A.
- Sparse Q main loop: about 254–256D and **~42A after seeding**; table: **1D+7A**. Roughly 9 main additions and 7 setup doublings removed. Recoding, sign handling, completeness branches, copies, and rare equality doubles are new overhead.
- Profile-weighted gross budget: ~3 percentage points from removing table scans, ~3 from fewer ordinary additions, ~1.3 from removing seven setup doublings, ~0.2 from fixed-base zero skips, plus small correction/leading-bit effects. **About 7–8% before replacement overhead** is a plausible rough budget, not a predicted benchmark outcome or a very-large-gain claim. There remains one almost-full Q doubling chain, the dominant cost. No arm64 percentage is claimed.

Simply guarding the old Booth loop's leading all-zero accumulator would save only ~1.3 doublings on average (roughly 0.2–0.3% API time), while inserting branches into every public window. It is useful for adversarial tiny scalars but not the strongest normal-workload candidate. Skipping interior zero-digit **doublings is not valid**: zeros still shift the accumulated coefficient. Dynamic wider windows/wNAF6+ would change table size/tradeoffs further; not added here to keep the experiment bounded.

The P256 candidate patch is confined to appending public-only functions in `nistec/p256_asm.go` and changing **only the body of ECDSA `verifyGeneric`** for capability dispatch. The permitted new call chain is:

```
verifyGeneric (validated public Q, r, s, hash)
  -> CombinedMultPublic
     -> p256BaseMultPublic       [existing fixed-base tables/formulas]
     -> p256ScalarMultPublic     [public wNAF / per-call odd Q table]
        -> p256PublicNAF
     -> existing complete final Add
```

**Do not replace or parameterize** the existing `ScalarBaseMult`, `ScalarMult`, `p256BaseMult`, or `p256ScalarMult`; do not redirect signing, nonce generation, key generation, ECDH, or shared secret multiplication to any public helper. Their original function bodies remain byte-for-byte unchanged in this patch. Existing private PCT may perform public verification, which is distinct from changing the signing/nonce multiplication path.

No public API change, reusable-key cache, mutable global state, or retained per-key table. No modification to key/point validation, r/s range validation, order inverse, hash truncation, DER parsing, final BytesX+mod-n comparison, or rare r+n acceptance.
